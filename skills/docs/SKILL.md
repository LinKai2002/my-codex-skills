# 项目文档工作流

## 1. 日常如何使用

启用 `$docs` 后按当前任务使用项目文档。单独收到 `$docs` 时，有正在进行的任务就沿用其目标和范围；尚无任务时等待具体需求。

例如，“阶段一完成了什么？”只需查阅对应模块的进展与验收依据。“把本次验证结果记到模块进展里”授权核实并更新该条目。“好像缺少项目总览”只需核实并说明缺口。用户要求分步审定时，每次只实施已认可的一步。

功能开发或阶段性交付完成时，检查本次变化涉及的项目总览、进展和模块说明，按当前任务范围增量更新相关条目。无需更新时，在交付中说明检查结果。全项目同步仍须用户明确要求。

## 2. 文档职责与读取顺序

先读适用的仓库指令和现有文档入口。查询可用能力时读总览，恢复任务时读进展，查实现说明或实验时再进入模块文档。文档足以回答普通查询时即可结束检索。写入前核对工作区与暂存区已有改动，保留他人正在编辑的内容。

| 默认位置 | 内容 | 更新时机 |
|---|---|---|
| `AGENTS.md` | 通用开发规则、修改范围、文档入口和读取顺序、阶段审定、逐文件汇报与提交许可 | 初始化时补齐入口和已认可的规则。同步时核对入口，协作规则的变更由用户决定。 |
| `PROJECT_OVERVIEW.md` | 项目背景、已交付模块清单，再逐模块介绍功能点、使用接口、关键函数和数据结构，包括必要的输入输出、单位和限制 | 可用功能或接口变化时 |
| `PROJECT_PROGRESS.md` | 按模块列出已完成与未完成事项，记录验收依据、当前进度、下一步和待决问题 | 状态、证据、阻塞或决定变化时 |
| `<模块目录>/README.md` | 模块范围、接口约定、关键流程、最小调用示例、验证命令和实验入口 | 模块建立且有具体内容可记录时创建，随后按实现和用法更新 |

沿用承担相同职责的现有文件及项目语言。仍用于交接的模块记录保存阶段细节，全项目进展记录结论并链接。阶段计划写明交付范围、接口和验收方式，重大架构与范围变更由用户决定。

实验归档于 `<模块目录>/experiments/<反映实验内容的名称>/` 或已有等价位置，记录目的、配置、假设、复现方法、结果及局限，注明本地产物与已归档文件。历史实验保留运行当时的配置、数值和图表。

## 3. 显式操作：init 和 sync

仅在用户明确要求执行相应项目级操作时启动以下流程。命令和含义明确的自然语言具有相同效力。依据请求的动作和范围判断；仅提及命令、询问用法、发现缺口或要求更新单个模块，都不触发全项目操作。

| 命令 | 等效的自然语言请求 | 行为 |
|---|---|---|
| `$docs init` | 请根据现有代码和文档补齐这个项目缺失的工程文档。 | 直接执行初始化。 |
| `$docs sync` | 请按项目现状同步全部现行文档。 | 直接执行全项目同步。 |

两种表达都遵守用户给出的限制。附有“先给我看初稿”或“先给我看差异”时，仅在对话中列出拟改路径、位置和具体内容，获认可后再写入。

初始化和同步时，将文档中的模块清单与当前目录、模块入口对照。按需使用已有符号索引或定向搜索核对公开接口、调用点、测试和验收记录。只有当前证据不足时才扩大阅读范围。

### init · 补齐缺口

1. 将现有文档对应到上表。复用原路径和有效正文，保留 README 中的安装等说明，补齐缺失的文件、必要章节和链接。
   创建或补充根目录 `AGENTS.md` 时，读取本 skill 的 [AGENTS.md 模板](assets/AGENTS.template.md)。以目标项目根目录为基准，将模板中的 `{{overview_path}}`、`{{progress_path}}` 替换为实际采用的总览和进展相对路径。不存在相应文档时先确定本次将创建的默认路径。
   没有 `AGENTS.md` 时按模板创建。已有文件时完整保留原文，仅在末尾追加缺失规则。逐条检查语义等价的已有规则，避免重复追加。发现冲突时保留已有规则，暂缓追加冲突的模板条款，在交付中列出双方内容和位置，交由用户决定；继续追加无冲突的缺失规则。重复初始化不得重复追加。Python 和数值条款仅适用于相关工作。
2. 空项目建立三个项目级入口。总览记录已知背景并注明“当前尚无已交付模块”。在进展中按实际状态登记已有构想及待审定事项。
3. 有代码的项目从必要的模块入口核实已交付能力。分别记录实现状态与验收状态。有具体内容时再建立模块说明，并从项目级文档链接过去。入口和内容已齐全时，报告检查结果即可。

### sync · 核对现状

1. 遍历现行模块，核对文档入口、总览、进展、模块说明和活跃交接记录，检查新模块有无遗漏。Git 差异可帮助定位近期变化，工作区干净时也要核对当前接口和模块清单。
2. 定向更新已过时或缺失的条目。例如接口更名时同步公开用法、示例和相关链接。发现文档约定与实际行为冲突且需要选择时，列出双方依据与位置，将决定留给用户，并继续处理独立的已核实事项。
3. 新实验改变当前结论时，在现行文档中链接新旧依据。文档准确时报告“已同步”。重复调用且项目状态相同时应产生零改动。

## 4. 如何验证与汇报

检查涉及的路径、链接和公开接口，对可安全复现的示例执行验证。区分历史验收记录、本轮实测与尚待验证的事项。

对照起始状态、实际写入和最终差异，逐文件报告“路径｜章节、函数或配置位置｜修改梗概”，覆盖同一文件内的独立修改以及新增、修改、删除、移动和重命名。移动时列出新旧路径。计入本轮未跟踪、被忽略及创建后移除的产物。零改动时说明检查范围和结果。

每次 Git 提交须取得用户对该次提交的明确许可。获准后核对暂存范围，报告提交号及所含文件。
